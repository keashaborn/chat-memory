# Governed Memory activation boundary

## Current decision

Do not activate the successor. Phase 9J prepares and proves an inactive,
stores-only installation and rollback system. It does not authorize production
stores, application services, routes, credentials, provider calls, or user
traffic.

Publishing the immutable controller runtime is preinstallation substrate, not
application activation. A successful disposable Linux proof demonstrates only
the fixed invocation-owned resources named by that proof. It cannot be reused
as authority to install or activate production.

## Phase 10 entry conditions

Before dormant production stores can be installed, a new signed authority must
bind the reviewed commit and tree, exact package and runtime receipts, pinned
image identities, fresh empty targets, fresh store credentials, exact global
lock, and a current read-only preflight. No legacy store, snapshot, mount,
credential, memory row, or vector may be reused.

Application activation is a separate approval. It additionally requires:

- installed successor HTTP and worker runtimes with fresh credentials;
- live Supabase session authority and owner isolation;
- chat capture, answer binding, attachment, and chat-only erasure verification;
- real provider and embedding validation under explicit authority;
- projection reconciliation and sequence-safe Qdrant repair;
- semantic calibration and an authorized pilot owner/scope;
- authenticated frontend verification;
- exact legacy reader/writer/timer/cron/router/admin quiescence for the required
  observation window;
- rollback evidence for both the stores and application routing change.

`brains.service` carries chat and LifeSwitch functions and must not be stopped
as a shortcut for memory exclusivity. Exclusive activation is achieved by
quiescing only legacy memory paths and routing only the successor memory path.

## Data guarantees

The successor starts with fresh empty PostgreSQL and Qdrant stores. PostgreSQL
is canonical and Qdrant is derived. Old claims, vectors, jobs, preferences,
review artifacts, compatibility state, and unprocessed legacy data are not
imported.

Only chat-owned conversations, transcripts, attachments, and conversational
memory participate in chat deletion. Account identities and structured
LifeSwitch data—including libraries, food logs, workouts, weightlifting
sessions, measurements, plans, and people data—remain outside that operation.

## Separate authority lanes

Source logging remediation, conversation-bridge changes, production store
installation, application deployment, activation, and legacy deletion are
separate authority lanes. A phase label or successful disposable proof does
not grant any of them.
